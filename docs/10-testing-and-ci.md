# 10 — Testing & CI

## 1. The hard requirement

**The default test suite passes on a machine with no network, no audio device, and no mpv
installed.** Everything below follows from that. It is what lets agents work in sandboxes and what
keeps CI honest.

| Layer | Technique | Runs in default CI |
| :-- | :-- | :-- |
| `loxia-core` | Pure unit tests + proptest on the reducer | yes |
| `loxia-emby` | `wiremock` + captured JSON fixtures | yes |
| `loxia-cache` | `tempfile` roots + fault injection | yes |
| `loxia-audio` | `MockEngine`; real-mpv tests behind the `mpv-tests` feature | yes (mock only) |
| `loxia-tui` | `insta` snapshots on `TestBackend` | yes |
| `loxia-player` (bin) | Scripted action-sequence integration tests | yes |
| End-to-end | Manual checklist against the live Emby server | release only |

## 2. The reducer is the primary test surface

Because state changes only through `apply(&mut AppState, Action) -> Vec<Effect>`, most behaviour is
a table:

```
given: an AppState fixture
when:  [Action, Action, ...]
then:  assert on the final AppState and on the concatenated Vec<Effect>
```

`loxia-core::test_support` provides the harness:
`Scenario::new(fixture).dispatch(a).dispatch(b).state()` / `.effects()`, plus fixture builders
(`AppState::fixture_miller_3col()`, `fixture_appears_on()`, `fixture_playing_queue()`, …) that every
other crate reuses behind the `test-support` feature.

The required test list is in `04-state-and-input.md` §10. Aim for **100 % of documented behaviours
covered**, not 100 % line coverage.

## 3. Property tests (`proptest`)

- Binding-string `parse(render(b)) == b` round-trip.
- Shuffle → unshuffle round-trip preserving the current track, over random queues.
- Sort stability: applying a profile twice equals applying it once.
- Ticks ↔ `Duration` round-trip within one tick.
- Path sanitiser: output never escapes the root, is never empty, is never a Windows reserved name.
- Config: an arbitrary valid `Config` → TOML → `Config` is the identity.

## 4. Fixtures

- `crates/loxia-emby/tests/fixtures/*.json` — captured, **token-redacted** responses. Redaction is
  enforced: a CI step greps the directory for token-shaped strings and private IPs and fails the
  build on a hit.
- `crates/loxia-core/src/test_support/` — shared `AppState` builders, exported behind a
  `test-support` feature.
- `crates/loxia-audio/tests/assets/` — a 3-second FLAC **generated by a build script**
  (`ffmpeg -f lavfi -i sine`), not committed as a binary.

## 5. Snapshot tests

`insta` + `ratatui::backend::TestBackend`.

- Fixed sizes only: 80×24, 120×30, 200×50. Never terminal-dependent.
- Fixed clock, fixed fixture data. **No `now()` on any snapshot path** — the classic source of
  flaky UI snapshots.
- Review deliberately with `cargo insta review`. A diff in an unrelated snapshot is a layout
  regression, not a nuisance to accept.
- The required snapshot list is in `07-ui-spec.md` §14.

## 6. Fault injection

- **Network:** wiremock scenarios for 401, 404, 429, 500, slow response, connection reset,
  malformed JSON, and a truncated stream.
- **Disk:** a read-only `tempfile` root; a simulated `ENOSPC` on a small tmpfs in the Linux job; a
  corrupted `session.json` and `cache_index.json`.
- **Audio:** `MockEngine` can be told to fail a `Load`, to stall, or to report a vanished device.

Every injected fault has an **asserted user-visible outcome** — a specific toast, or a specific
state transition. The point is that nothing crashes and nothing silently swallows an error.

## 7. CI matrix

`ci.yml`, on push and PR:

| Job | Runner | Steps |
| :-- | :-- | :-- |
| `lint` | ubuntu | `fmt --check`, `clippy -D warnings`, `cargo deny check`, fixture-secret grep |
| `test-linux` | ubuntu | `cargo test --workspace` |
| `test-macos` | macos | `cargo test --workspace` |
| `test-windows` | windows | `cargo test --workspace` — catches path-sanitiser and `dirs` bugs |
| `build-release` | all three | `cargo build --release`, to catch platform-only compile errors early |

Caching via `Swatinem/rust-cache`. One concurrency group per branch, cancel-in-progress.
`release.yml` runs on tags: the cargo-dist matrix plus the licence-artifact checks from
`11-packaging.md` §6.

## 8. Release QA checklist (per platform)

The condensed per-platform list below is the release gate. For a **full feature sweep** — every
view, every binding, and a regression check for each defect previously found in live use — work
through `14-manual-test-plan.md` instead; this list is a subset of it.


1. Fresh install on a clean machine or VM — no mpv pre-installed on Windows; mpv from the package
   manager on macOS and Linux.
2. First run creates a config; connect to a server both with and without custom headers.
3. Browse all ten tabs; verify the ALBUMS / APPEARS ON split on a known compilation, and that
   Album Artists is the shorter list (album-credited only) against Artists.
4. Play an album gaplessly end to end; verify play counts increment in the Emby web UI.
5. `a` versus `A` on an appears-on album — verify the track sets differ correctly.
6. Shuffle, unshuffle, apply a sort profile, save the queue as a playlist; verify in the Emby web UI.
7. Play a track with an `.lrc` sidecar; verify synced lyrics scroll in step.
8. Download an album; disconnect the network; browse and play it offline; reconnect; verify the
   buffered play counts land.
9. Device hot-swap mid-track; EQ adjust; ReplayGain cycle.
10. Sleep timer (end-of-track and 15-minute variants) including fade-out.
11. Zen mode with album art in Kitty, and in a terminal with no graphics support.
12. Media keys; desktop notifications.
13. Quit and relaunch — queue, position, tab, and volume restored, **paused**.
14. Resize to 80×24 and to a very large window; resize during playback.
15. Introduce a deliberate keybinding conflict in `config.toml`; verify the startup toast, the
    Settings badge, the log lines, and that the app still starts and works.
16. Kill the terminal (SIGHUP) — verify no orphan process and no corrupt index files.
17. Uninstall; verify what remains on disk is only user data, and that it is documented.

## 9. Performance targets

Against a 50,000-track library:

| Metric | Target |
| :-- | :-- |
| Frame render at 200×50 | < 16 ms |
| Column page load (200 items) over LAN | < 400 ms |
| Idle CPU | < 1 % |
| Playing CPU (excluding mpv's decode thread) | < 3 % |
| RSS with 20 decoded artwork images cached | < 150 MB |
| Startup to interactive (excluding the first request) | < 300 ms |

Measured with `hyperfine` for startup and a hidden `--bench-render` flag that renders N frames from
a fixture and reports p50/p99. Re-run at the end of phases 04, 07, and 10.
